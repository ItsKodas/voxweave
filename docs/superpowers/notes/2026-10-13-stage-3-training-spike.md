# Stage 3 spike: native Windows RVC v2 training on the RX 7900 XTX (ROCm PyTorch)

Date: 2026-10-13. Everything below was run on this machine, inside `D:\Projects\AI Voice\spike\stage3\`.

## 1. Verdict

**Works, with caveats.** An RVC v2 40k pitch model trains end to end natively on Windows on the RX 7900 XTX using
AMD's official `torch 2.9.1+rocm7.2.1` wheels, by command line only, in mixed precision (fp16 autocast + GradScaler),
with RMVPE pitch extraction and HuBERT feature extraction also on the GPU. The resulting small `.pth` is accepted
unchanged by the project's existing exporter (`tools/export_rvc_onnx.py`, RVC tag 2.2.231006 + patch), the exported
ONNX runs through the app's `RvcEngine` on DirectML producing finite audio of exactly the input length, and the faiss
index loads and blends through `blend_index`. No WSL, no driver change, no system-wide install was needed: the
installed driver (32.0.31041.1004, Adrenalin 26.8.1) already satisfies AMD's 26.2.2 minimum. The caveats are two
source patches to the RVC clone that the worker should carry: (1) **required for usable speed**: dilated
convolutions are about 60x slower than normal ones on this ROCm build, which made training 3.4x slower until the
generator's ResBlock was rewritten to an exactly equivalent non-dilated form; (2) **recommended**: the pinned
upstream commit has a preprocessing regression that silently drops audio in any clip containing an internal pause.
Only synthetic audio and runs of 2 to 8 epochs were tested; voice quality and multi-hour stability are untested.

## 3. Environment variables for every stage

Working directory for every stage: the RVC root (`D:\Projects\AI Voice\spike\stage3\rvc`). The scripts use relative
paths (`./i18n/locale`, `./logs`, `assets/...`), so the cwd is not optional. All set by `scripts/run_stage.py`:

| Variable | Value | Why |
| --- | --- | --- |
| `PYTHONPATH` | RVC root | Scripts are run as files (`python train/train.py`) and import `infer`, `train`, `configs`, `tools`, `i18n` from the root. |
| `PYTHONSAFEPATH` | `1` | **Required.** Without it Python puts `train/` first on `sys.path` and `import train` resolves to `train/train.py` (`ImportError: cannot import name 'utils' from partially initialized module 'train'`). Upstream avoids this with its portable `runtime\python.exe -I`. Equivalent: `python -P`. |
| `RVC_CUDA_GRAPH` | `0` | `webui.py` sets this for training; also skips the CUDA-graph probe that `configs/config.py` runs at import. |
| `ROCM_SDK_TARGET_FAMILY` | `custom` | Silences a harmless failure: the ROCm SDK shells out to `offload-arch.exe` and the launcher breaks on the space in `D:\Projects\AI Voice` (`AI: Unknown command line argument 'Voice\...offload-arch.exe'`). The fallback is `custom` anyway (the only family in these wheels). |
| `MIOPEN_USER_DB_PATH`, `MIOPEN_CUSTOM_CACHE_DIR` | `<spike>\cache\miopen\db`, `...\cache` | MIOpen otherwise writes its kernel/find caches to `C:\Users\<user>\.miopen`. Must be a **persistent** folder: the cache removes minutes of warm-up on later runs. |
| `MIOPEN_LOG_LEVEL` | `3` | Otherwise hundreds of `MIOpen(HIP): Warning [IsEnoughWorkspace] ...` lines flood the output. |
| `HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE` | `1` | Belt and braces; nothing needs the network (section 10). |
| `HF_HOME`, `TORCH_HOME`, `MPLCONFIGDIR`, `NUMBA_CACHE_DIR` | folders under `<spike>\cache` | Keep caches off C:. |
| `PYTHONIOENCODING`, `PYTHONUNBUFFERED` | `utf-8`, `1` | Log lines can contain non-ASCII; unbuffered for live progress. |

Not redirected: MIOpen also creates a zero-byte lock file in `%TEMP%\miopen-lockfiles\`. Set `TEMP`/`TMP` for the
worker if that matters (`webui.py` itself points `TEMP` at `<root>\TEMP`).

Facts that matter for the worker:

- **Filelist line** (single speaker, pitch): `wav|feature|coarse_f0|f0|speaker_id`, for example
  `D:\\Projects\\AI Voice\\spike\\stage3\\rvc/logs/spike1/0_gt_wavs/10_2.wav|D:\\...\\rvc/logs/spike1/3_feature768/10_2.npy|D:\\...\\rvc/logs/spike1/2a_f0/10_2.wav.npy|D:\\...\\rvc/logs/spike1/2b-f0nsf/10_2.wav.npy|0`
  (absolute paths, backslashes doubled exactly as `webui.py` writes them; spaces in the path are fine). Two extra
  lines point at `logs/mute/0_gt_wavs/mute40k.wav`, `logs/mute/3_feature768/mute.npy`, `logs/mute/2a_f0/mute.wav.npy`,
  `logs/mute/2b-f0nsf/mute.wav.npy`. Lines are shuffled. Only segments present in all four folders are listed.
- **Config**: for v2 at 40k `webui.py` copies `configs/v1/40k.json` (there is no `v2/40k.json`; the v2 difference is
  the 768-dim feature folder and `-v v2`). An existing `logs/EXP/config.json` is reused, not regenerated.
- **Flags**: `-te` is where training stops, `-se` the checkpoint interval in epochs, `-l 1` keeps only the latest
  checkpoint pair, `-sw 1` also writes an inference-ready `assets/weights/EXP_e<epoch>_s<step>.pth` (55 MB) at every
  save, `-c 1` caches the dataset on the GPU (no speed gain measured here). `-g 0` is the GPU id.
- **The final small model** `assets/weights/EXP.pth` (55 MB, fp16 weights, keys `weight`, `config`, `info`, `sr`,
  `f0`, `version`) is written only when the epoch counter reaches `-te`; the process then ends itself with
  `os._exit(0)`. `assets/weights/` must already exist: `savee` catches its own exception and returns the traceback
  as text, so a missing folder shows up only as a log line that does not end in `Success`.
- **Stage 7 equals stage 5's output**: the model extracted from `G_34.pth` had tensors identical to the
  `spike1.pth` the trainer wrote at the same step (`scripts/inspect_pth.py`).
- Stages 2 and 3 skip segments whose outputs already exist, so they are restartable. Stage 6 skips if an `added_*`
  index for the experiment already exists (delete it to rebuild after adding data).
- Stage 1 returns exit code 0 even when files fail; check `preprocess.log` for `[Failed]`.
- Stage 3 ignores a `cpu` device argument when a GPU is available (it re-selects CUDA itself).
- RMVPE ran on the GPU, so no pitch fallback was needed. For reference the CPU form is
  `PY train/dataset/extract_f0.py cpu "R/logs/EXP" 8 rmvpe` (22.6 s for 58 segments, but 9.3 GB RAM across 8 workers).

- `[5, 0.0001]` is `[global_step, learning_rate]`; it and the `loss_disc=...` line are **not translated**, nor is
  `Saving model and optimizer state at epoch N to <path>`. The `Training epoch: N [P%]` and `====> Epoch: N [time] | (elapsed)`
  lines **are translated**.
- The step/loss block appears only when `global_step % log_interval == 0`. `log_interval` is 200 in
  `configs/v1/40k.json`, so with small datasets a loss line appears once every several epochs. It is a per-experiment
  setting: edit `train.log_interval` in `logs/EXP/config.json` (the samples above used 5). Each logged step also
  renders three spectrogram images for TensorBoard, so do not set it to 1.
- The reliable per-epoch signal is the `====> Epoch: N` line (one per epoch, always). Epoch progress within an epoch
  is the `[P%]` on the translated line.
- `loss_mel` is clamped to 75 and `loss_kl` to 9 for display, hence the repeated `9.000`.
- The TensorBoard event file has every logged scalar (`loss/g/total`, `loss/d/total`, `loss/g/mel`, `loss/g/kl`,
  `loss/g/fm`, `learning_rate`, `grad_norm_g`, `grad_norm_d`) at the same interval.
- A resumed run prints `INFO:EXP:Loaded checkpoint './logs\EXP\G_2333333.pth' (epoch 2)` (untranslated) instead of
  the two `Loaded ... pretrained model` lines.

## 6. Resume and cancel

**Resume** is automatic and needs no flag: at start `train.py` looks for the highest-numbered `D_*.pth` and `G_*.pth`
in `logs/EXP/` and loads model plus optimizer state; if that raises for any reason it falls back to the `-pg/-pd`
pretrained files and starts at epoch 1. Proven twice: (a) `-te 1` then the same command with `-te 2`
(`logs/s4_train_e1_bs4.log`, `logs/s5_train_resume_e2_bs4.log`), and (b) a hard kill in the middle of epoch 3
followed by `-te 4` (`logs/kill_test.log`, `logs/b10p_resume_after_kill.log`).

Behaviour to design around:

1. **A resumed run repeats the number of the last saved epoch.** The checkpoint stores the epoch it was saved at,
   and the loop restarts at that same number with `global_step = (epoch - 1) * steps_per_epoch`. After saving at
   epoch 1 and resuming to `-te 2`, the log shows `Training epoch: 1` again (starting from the epoch-1 weights),
   then epoch 2. No work is lost, but each resume adds one extra epoch of training that the counter does not count,
   and with `-l 0` the repeated epoch overwrites `G_<step>.pth` of the same step number.
2. **A failed checkpoint load is silent.** The fallback to pretrained is a bare `except`. The worker should treat a
   resume without the `Loaded checkpoint '...G_...pth' (epoch N)` line as an error, otherwise a damaged checkpoint
   quietly restarts training from scratch.
3. Only epochs that were saved (`epoch % -se == 0`) can be resumed from. With `-se 1` that is every epoch at a cost
   of about 1.2 s per save.
4. Checkpoints are large: `G` 438 MB + `D` 857 MB = 1.3 GB per saved epoch. `-l 0` keeps every one of them (spike1
   used 2.6 GB for two epochs). Use `-l 1` (fixed names `G_2333333.pth`, `D_2333333.pth`, overwritten in place).

**Cancel.** `train.py` has no graceful stop: no signal handler, no stop file. `webui.py` simply kills the process
tree. The tree observed here was:

```
venv\Scripts\python.exe   (9 MB; uv's launcher shim, this is the PID that Popen returns)
  └─ python.exe           (the trainer, about 2.7 GB RSS)
       └─ 4 x python.exe  (DataLoader workers, multiprocessing spawn, about 570 MB each)
```

`taskkill /PID <shim pid> /T /F` ended all six (exit code 1 for the parent) and dedicated GPU memory returned to the
desktop baseline within seconds. Killing only the PID from `Popen` would leave the trainer running, because that PID
is the shim. State left behind: the last completed checkpoint pair, `train.log`, the event file; no
`assets/weights/EXP.pth`. To get a usable model after a cancel, run stage 7 on the checkpoint, or resume.

Two cleaner options: choose `-te` as the stopping point (the process saves the small model and exits by itself), or
kill only right after an `====> Epoch: N` line. The save is not atomic (`torch.save` straight onto the final file
name, about 1 s for both files), so a kill that lands between a `Saving model and optimizer state` line and the
following `====> Epoch` line can leave a truncated checkpoint; with `-l 1` that is the only copy.

## 10. Answers for the worker design

**Can training use the app's existing 16 kHz and 48 kHz clip files directly?** Use the 48 kHz originals, through
RVC's own preprocess; the app's 16 kHz files cannot be used.

- Preprocess takes each input file, resamples it to 40 kHz with ffmpeg, applies a 48 Hz high-pass, splits at
  silences (400 ms below -42 dB, chunks of at least 1.5 s, up to 500 ms of silence kept), cuts each chunk into 3.7 s
  windows with 0.3 s overlap, and normalises each window as `0.75 * (x / peak * 0.9) + 0.25 * x`. It writes that
  window at 40 kHz (`0_gt_wavs`, the training target) and the *same* window resampled to 16 kHz (`1_16k_wavs`, the
  input for pitch and HuBERT). The two must be the same cut and the same gain, sample-aligned, so the app's
  whole-clip, un-normalised 16 kHz `NNNN.wav` files do not fit, and reusing them would save nothing.
- **Do not point preprocess at the app's `clips/` folder.** It processes every file in the folder. Tested on a
  folder laid out like the app's (`NNNN.orig.wav`, `NNNN.wav`, `NNNN.txt`): the 16 kHz copies were sliced as
  additional training data (every clip twice, once upsampled from 16 kHz) and each `.txt` produced a
  `[Data slicing][Failed]` traceback, with exit code 0. The worker must hand over a staging folder containing only
  the `*.orig.wav` files (hard links are enough). Output segment names are `<position of the file in the sorted
  folder listing>_<n>.wav`, not the clip number.
- The app's clips are already trimmed and silence-split at 300 ms / -40 dB, so RVC's slicer will usually keep each
  one whole; recorded takes of up to 20 s with pauses are exactly the case patch 8.2 protects.

## 11. Open risks

1. **Only synthetic audio, 2 to 8 epochs.** The pipeline is proven; voice quality, convergence over 100+ epochs and
   stability over hours on ROCm are not. A soak run on real recordings should be the first thing stage 3 does.
2. **Upstream does not test this torch.** Its requirement files pin torch 2.7.1 CUDA and say to stay below 2.8.
   Everything ran on 2.9.1+rocm, but a future upstream change could assume CUDA-only behaviour.
3. **Two carried patches** against a moving `main` branch (the pinned commit is from 2026-08-04). Pin the commit.
   Without 8.1 training still works, at about a third of the speed.
4. **MIOpen warm-up and noise.** Each new tensor shape costs seconds the first time (first-ever steps took 13 s to
   4.5 min depending on batch size; a later run with a warm cache took 5 s). Real speech has more varied segment
   lengths than this synthetic data, so the first epochs of the first real run will be slower than the table. One
   non-fatal line appeared in one of the 13 training runs:
   `MIOpen(HIP): Error [EvaluateInvokers] ... Invalid elapsed time detected in EvaluateInvokers, failed condition: elapsed <= 0`.
   A parser that treats any line containing `Error` as fatal would misfire on it.
5. **Resume quirks** (section 6): repeated epoch number, silent fallback to pretrained when a checkpoint cannot be
   read, non-atomic saves, single checkpoint copy with `-l 1`.
6. **Silent partial failure**: preprocess exits 0 with failed files; `savee` reports a failed model write only as
   log text. The worker has to check outputs (segment count, existence and size of `assets/weights/EXP.pth`).
7. **Log language follows the Windows locale.** English here. Parse the untranslated lines where possible.
8. **Disk**: 1.3 GB per checkpoint pair, 55 MB per small model, the environment is about 6.5 GB (uv cache holding
   the venv's files) and the pretrained files 0.6 GB.
9. **GPU sharing**: the desktop already held about 3.6 GB of VRAM during the spike; training at batch 8 adds 6 to
   7 GB. The design already stops live mode while training.
10. **Space in the install path** broke one ROCm helper (cosmetic, worked around). Everything else, including
    filelists with spaces, was fine, and that was the only path tested.
11. **Driver coupling**: these wheels need Adrenalin 26.2.2 or newer according to AMD; 26.8.1 works. A future driver
    or ROCm release changing this is outside the app's control; the setup check should test
    `torch.cuda.is_available()` in the training venv rather than a version number.
12. Not evaluated: whether `rocm_sdk_devel` (233 MB) is needed at run time; training at 48k or 32k; training without
    the pretrained base; `harvest`/`pm` pitch for training (RMVPE worked, so no fallback was tried beyond RMVPE on CPU).
